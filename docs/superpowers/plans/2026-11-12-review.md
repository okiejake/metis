# Review Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Review page that lists everything Metis cannot yet account for — transfers counted as spending, uncategorized spending, unbudgeted categories, untracked repeats — and settles each with one decision per merchant.

**Architecture:** One definition of spending and one merchant key are shared by Budget, the recurring detector and Review. Review's decisions are stored per merchant and applied to stored rows and to every later import; every action is recorded so it can be undone. New logic lives in `merchants.py` (pure) and `review.py`; schema stays in `services.init_db`; the page reuses shared template macros.

**Tech Stack:** Python 3.12, FastAPI, Jinja2, DuckDB 2.0, pytest. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-11-12-review-design.md`

## Global Constraints

- All test data synthetic: obviously fake names ("Acme Grocer"), round amounts. No real data anywhere (`CLAUDE.md` data policy).
- Names, one per thing, everywhere (nav, headings, buttons, URLs, identifiers): page **Review** at `/review`; lists **Transfers, Categories, Budgets, Recurring**; actions **Confirm, Dismiss, Skip**; measure **Categorized**, a percent.
- Copy: a list is a heading, a count and a total, with no description; a row is a name and one line of facts; no tooltip needed to operate; an empty list is not shown; when all four are empty the page says "Nothing to review."; Review has no tagline or intro paragraph.
- Every template URL is written after `{{ base_path() }}` (`tests/test_base_path.py` fails otherwise). Routes and redirects use plain paths.
- A category picked by hand for one charge (`category_via IS NULL` with a category) is never overwritten.
- Marking rows as transfers must not change any account's balance or the cash forecast.
- Do not refactor parts of other pages that Review does not use. Existing pages' copy and layout stay as they are.
- Run tests with `.venv/bin/python -m pytest -q`. The suite is green before Task 1 (145 passed).

## Review Focus

1. **Deleting a category a merchant decision points to** — the decision goes with it; later imports from that merchant arrive uncategorized, not pointed at a missing category. (Task 3)
2. **A merchant with a category rule and a Review decision** — the decision wins for rows it set; `resync_category_rules` never releases or steals a row the decision set. (Task 3)
3. **Undo after more imports arrived** — rows the decision categorized or marked since it was made revert too. (Tasks 3, 4)
4. **No spending in the date range, or all of it categorized** — the meter is not shown, the page says "Nothing to review.", the nav shows no number. (Tasks 5, 7)
5. **A stale Confirm** (double submit, or a second tab after the row is gone) — no error, no duplicate action; it reports nothing left to change. (Task 7)

### Task 3: Review storage and category decisions

**Files:**
- Create: `review.py`
- Modify: `services.py` (`init_db` schema; new `create_category`), `routes/categories.py` (create uses `create_category`; delete removes decisions), `routes/imports.py` (apply decisions after import)
- Test: `tests/test_review_decisions.py`

**Interfaces:**
- Consumes: `merchant_key` (Task 1), `spending_parts` (Task 2).
- Produces:
  - Schema: `merchant_decisions(id, user_id, merchant_key, kind TEXT, category_id BIGINT, created_at, UNIQUE(user_id, merchant_key))` with `kind` `'category'` or `'transfer'`; `review_actions(id, user_id, kind TEXT, payload TEXT, created_at)` with JSON payload; column `imported_transactions.decision_id BIGINT`.
  - `services.create_category(user_id: int, name: str, color: str = DEFAULT_CATEGORY_COLOR) -> int`, raising `ValueError` on a blank or duplicate name.
  - In `review.py`:
    - `confirm_category(user_id: int, key: str, category_id: int) -> Optional[int]`
    - `set_charge(user_id: int, tx_id: int, choice: Union[int, str]) -> Optional[int]`, where `choice` is a category id or `"transfer"`
    - `apply_review_decisions(user_id: int) -> int`
    - `record_action(user_id: int, kind: str, payload: Dict[str, Any]) -> int`
    - `undo(user_id: int, action_id: int) -> str`

  The `Optional[int]` functions return the action id, or `None` when nothing was left to change.

Rules:
- `confirm_category` upserts the merchant's decision, then sets `category_id`, `category_via = 'merchant'` and `decision_id` on every row of that merchant (all history, matched by `merchant_key`) whose effective category is `None`.
- `apply_review_decisions` does the same for every decision. It is idempotent, so it runs after every import, in `routes/imports.py`, before `apply_category_rules`. `apply_category_rules` already skips rows whose `category_via` is not `NULL`/`'rule'`.
- `set_charge` with a category sets that one row's category by hand (`category_via = NULL`) and records the previous values.
- `undo` of a decision deletes it and clears category, `category_via` and `decision_id` on every row carrying its `decision_id`, including rows from later imports. `undo` of a charge restores the recorded values.
- Deleting a category also deletes the merchant decisions that name it.

### Task 4: Transfers

**Files:**
- Modify: `review.py`
- Test: `tests/test_review_transfers.py`

**Interfaces:**
- Consumes: Task 3's schema, `record_action`, `undo`, `apply_review_decisions`; `services.PAYMENT_MATCH_WINDOW_DAYS` (7).
- Produces:
  - `paired_outflows(user_id: int, window_start: date, window_end: date) -> Dict[int, Dict[str, Any]]`: an outflow's `tx_id` maps to its arrival `{tx_id, account_id, account_name, account_type}`.
  - `confirm_transfer(user_id: int, key: str) -> Optional[int]`.
  - `set_charge(..., "transfer")` now supported.

Rules:
- **Pairing.**
  - An outflow is a non-transfer row with `amount < 0` on a non-card account, dated in the window.
  - Its arrival is a row with `amount` equal to `-outflow.amount` (±0.005) on a different account, within 7 days. The arrival may already be marked as a transfer, as a card payment is at import.
  - Pairing is one-to-one, closest date first.
  - Outflows on a card are never listed or marked, so card statements are untouched.
- **Confirm.**
  - Upserts a `'transfer'` decision.
  - Sets `is_transfer = TRUE` and `decision_id` on the merchant's unmarked non-card outflows, all history.
  - Marks each one's paired arrival the same way when the arrival is on a non-card account and not already a transfer. An arrival on a card is left alone.
- **Later imports.** `apply_review_decisions` repeats both steps, and marks an arrival imported after its outflow.
- **Undo** sets `is_transfer = FALSE` and clears `decision_id` on every row carrying it.

### Task 5: The four lists and the meter

**Files:**
- Modify: `review.py`
- Test: `tests/test_review_lists.py`

**Interfaces:**
- Consumes: Tasks 1–4; `build_budget_summary`, `detect_recurring_suggestions`, `load_dismissed_suggestion_keys`.
- Produces:
  - `build_review(user_id: int, window_start: date, window_end: date) -> Dict[str, Any]`, keys:
    - `meter`: `{percent: Optional[int], spending: float, uncategorized: float}`
    - `transfers`: `[{key, name, count, total, arrived_in, charges}]`
    - `categories`: `[{key, name, count, total, suggested_category_id, charges}]`; each charge is `{tx_id, tx_date, description, amount, split_count}`
    - `budgets`: `[{category_id, name, color, typical, suggested}]`
    - `recurring`: the detector's suggestions, unchanged
    - `waiting`: int
  - `suggested_budget(monthly: List[float]) -> Optional[float]`.
  - `review_waiting_count(user_id: int) -> int`.
  - Dismiss keys in `dismissed_suggestions`: `"transfer:<merchant key>"` and `"budget:<category id>"`. Recurring keeps its own keys.

Rules:
- **Meter.** `percent = round(100 * (spending - uncategorized) / spending)`, or `None` when `spending <= 0`, from `spending_parts`.
- **Transfers.**
  - A merchant group is listed when at least half its in-window non-card outflows are in `paired_outflows`.
  - Groups that are dismissed, or already have any decision, are excluded.
  - `arrived_in` is the most common arrival account's name.
- **Categories.**
  - Uncategorized parts grouped by `merchant_key`, with a total above 0, largest first.
  - Keys listed under Transfers are excluded.
  - `suggested_category_id` is the most common own category among the merchant's categorized rows, any date, else `None`.
- **Budgets.**
  - Categories in the window's `build_budget_summary` with `has_target` false, `actual > 0` and an `id`, not dismissed.
  - `typical` is the median monthly spending over the last six complete calendar months before today, counting only months on or after the first imported row. A month with no spending counts as 0.
  - `suggested = suggested_budget(those months)`.
- **Recurring.** `detect_recurring_suggestions(user_id)`.
- **Waiting.** The total row count across the four lists.
- **`review_waiting_count`** uses the shared saved window (`resolve_forecast_window(user_id)`). It memoizes per user on a cheap stamp: one query returning `COUNT(*)`, `MAX(id)`, `SUM(COALESCE(category_id, 0))` and `SUM(CAST(is_transfer AS INT))` over `imported_transactions`, plus counts of `merchant_decisions`, `dismissed_suggestions`, `recurring_items`, `categories`, and `SUM(budget_amount)`.

### Task 7: The Review page and its actions

**Files:**
- Create: `routes/review.py`, `templates/review.html`
- Modify:
  - `app.py`: include the router
  - `services.py`: `redirect_with_message`
  - `templates/base.html`: Undo in the flash message
  - `routes/recurring.py`: `next_path`, and record the action for suggestions
  - `routes/splits.py`: `next`
- Test: `tests/test_review_page.py`

**Interfaces:**
- Consumes: Tasks 3–6.
- Produces:
  - Routes:
    - `GET /review`
    - `POST /review/merchants/confirm` (`key`, `choice`, `new_category_name`, `list`)
    - `POST /review/merchants/dismiss` (`key`)
    - `POST /review/charges/{tx_id}` (`choice`, `new_category_name`)
    - `POST /review/budgets/confirm` (`category_id`, `amount`)
    - `POST /review/budgets/dismiss` (`category_id`)
    - `POST /review/recurring/dismiss` (`suggestion_key`)
    - `POST /review/undo/{action_id}`
    - `POST /review/restore`
  - `redirect_with_message(path: str, message: str, is_error: bool = False, undo: Optional[int] = None)`. It keeps a `#fragment` after the query (`/review#categories` → `/review?msg=…&err=0&undo=7#categories`).

Rules:
- **Page.** `GET /review` renders `build_review` for `resolve_forecast_window`, passing `show_forecast_window_form=True` and `window_form_action="/review"`.
  - Order: the meter, then tiles linking to `#transfers`, `#categories`, `#budgets`, `#recurring` (shown only for non-empty lists), then the lists in that order. A "Restore dismissed (N)" link appears when `count_dismissed_suggestions > 0`.
  - All four lists empty: "Nothing to review." and no meter.
- **Actions** redirect to `/review#<list>` with the action's undo id. `choice = "new"` creates the category first, with `create_category`. A Confirm that changed nothing (`None`) redirects with "Nothing left to change" and no undo.
